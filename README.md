# VitalAI

> Upload your blood report. Get your personalized health plan.

VitalAI is a full-stack web app that reads a blood test report (PDF or image), combines it with the user's profile, and returns a structured health analysis plus a personalized diet and exercise plan — generated by an LLM.

- **Frontend:** React 18 + Vite + Tailwind CSS
- **Backend:** Node.js + Express
- **AI:** Google Gemini (`gemini-1.5-flash`) — free tier, no credit card required. The AI layer is modular; swap in Anthropic Claude, OpenAI, Groq, or any other provider by replacing `server/services/aiService.js`'s `createDefaultClient`.
- **Extraction:** `pdf-parse` for PDFs, `tesseract.js` for images
- **PDF export:** `jspdf`

## Setup

### Prerequisites
- Node.js 18+ (tested on 20)
- npm 10+

### 1. Backend

```bash
cd server
npm install
cp .env.example .env
# edit .env and set GEMINI_API_KEY (get a free key at https://aistudio.google.com/apikey)
npm run dev
```

The API listens on `http://localhost:5000`.

**No API key?** Set `USE_MOCK_AI=true` in `server/.env` to use a deterministic mock plan instead. The UI works end-to-end either way.

### 2. Frontend

```bash
cd client
npm install
cp .env.example .env
npm run dev
```

The app runs on `http://localhost:5173` and talks to the API at the URL in `client/.env`.

## API

### `POST /api/analyze`

`multipart/form-data`:

| Field | Type | Description |
|---|---|---|
| `file` | File | Blood report — PDF, JPG, or PNG. Max **10 MB**. |
| `userProfile` | string (JSON) | Stringified profile (see shape below). |

**Profile shape:**

```json
{
  "age": 32,
  "gender": "Male",
  "weight": 78,
  "height": 175,
  "diet": "Vegetarian",
  "activity": "Moderately Active (3-5 days/week)",
  "goals": ["Lose Weight", "Improve Energy"],
  "conditions": "mild hypertension"
}
```

**Response:** `200 OK` with the structured plan (`healthScore`, `bloodMarkers[]`, `keyFindings[]`, `bmi`, `bmiCategory`, `dailyCalories`, `dietPlan{}`, `exercisePlan{}`).

**Errors:**

| Status | Meaning |
|---|---|
| 400 | Missing file, missing/invalid `userProfile`, or required profile fields missing |
| 413 | File exceeds 10 MB |
| 500 | Upstream AI failure with `allowFallback=false` (the route currently falls back to a mock by default, so this is rare) |

### `POST /api/quick-plan`

`Content-Type: application/json` — same profile shape as above, sent directly in the body (no file). Returns the same plan structure but with generic blood markers (since no report was provided). BMI-based only.

### `POST /api/contact`

`Content-Type: application/json`:

| Field | Type | Description |
|---|---|---|
| `name` | string | Sender name |
| `email` | string | Sender email (reply-to) |
| `message` | string | 5–4000 chars |

Sends email to `curiolightforyou@gmail.com` if SMTP is configured, otherwise saves to `server/data/contact-submissions.json`.

### `POST /api/visit`

Records a unique visitor (hashed IP + User-Agent). Returns current stats.

### `GET /api/stats`

Returns `{ uniqueVisitors, totalVisits, reportsChecked, quickPlansChecked }`.

### `GET /api/health`

Returns `{ ok: true, name: "VitalAI", version: "1.0.0" }`.

## How it works (request flow)

1. The user uploads a PDF or image and fills out the profile form.
2. The frontend posts to `/api/analyze` with the file and profile JSON.
3. The route parses the multipart body, validates the profile, and dispatches to `pdfParser` or `ocrService` based on mimetype/extension.
4. Extracted text + profile go to `aiService.generateHealthPlan`, which builds a structured prompt and calls Gemini in JSON mode.
5. The response is JSON-parsed (with markdown-fence stripping as a safety net) and returned.
6. If extraction returns an empty string, the prompt explicitly tells the model the report could not be parsed — it still produces a plan based on the profile and notes the parse failure in `keyFindings`.
7. If the AI call fails (no key / rate limit / network error), the service falls back to a deterministic mock plan and prepends the error to `keyFindings` so the user knows.

## Testing

Both stacks have a real test suite — run from the respective directory.

```bash
# Backend - 29 tests across 4 files (Vitest + Supertest)
cd server && npm test

# Frontend - 23 tests across 3 files (Vitest + React Testing Library)
cd client && npm test
```

**Backend test coverage:**
- `aiService` — prompt building, JSON parsing (raw / fenced / mixed-in text), BMI math, diet-aware meal selection, mock fallback, injected-client path
- `pdfParser` & `ocrService` — happy path, empty output, throw-as-empty-string graceful failure
- `analyzeRoute` — 400s for missing file / missing profile / missing fields; correct PDF vs image dispatch; 500 on AI failure; graceful empty-extraction handoff

**Frontend test coverage:**
- `Uploader.validateFile` — accepted types, 10MB cap, missing-mimetype-but-valid-extension fallback
- `UserForm` — `validateUserProfile` boundary cases, inline error rendering, submit-on-valid, multi-select goal toggling
- `BloodReport` — score categorization (`scoreColor`), table rendering, key findings, missing-markers empty state, disclaimer present

## Design notes

- **Color scheme** — deep navy (`#0A0F1E`) + teal accent (`#00D4AA`) + white, defined in `tailwind.config.js` so all components share the palette.
- **Font** — Inter from Google Fonts, preconnected for speed.
- **Step progress** — a `ProgressBar` in the header shows the user's position across the four steps.
- **Toasts** — a lightweight `ToastProvider` exposes `useToast().show(message, type)` for error/success notifications.
- **Medical disclaimer** appears on every result tab and in the footer.
- **Animations** — `fade-in`, `slide-up`, and `pulse-glow` keyframes defined in Tailwind config.

## Swapping the AI provider

`aiService.generateHealthPlan(text, profile, options)` accepts an injected `client` with the shape `{ generateContent(prompt) -> Promise<string> }`. To use Anthropic Claude, OpenAI, Groq, etc., add a new factory next to `createDefaultClient` and wire it up via env var — the rest of the pipeline (prompt, JSON parsing, fallback, normalization) is provider-agnostic.
